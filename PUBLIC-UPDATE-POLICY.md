# Owner-approved updates

1. Select an explicitly approved project summary and immutable evidence checkpoint. A new private file or commit is not permission to publish it.
2. Work in a separate private candidate directory. Preserve original images and documents. Stage only the chosen screenshot/document copies.
3. Review source claims, visual concepts, test environments and experimental/device acceptance separately. Check pixels, text, metadata and embedded PDF objects for private records, identifiers, credentials, addresses, internal links and paths.
4. Rebuild the static candidate. Verify all links, pages, galleries, downloads and responsive/keyboard behavior. Review changed screenshots and render every changed PDF page.
5. Produce the exact final file list, sizes, hashes, changes and limitations. Obtain owner approval for that concrete content and a separate explicit public-release authorization identifying the destination and revision/digest.
6. Only then update this repository with those approved files. Never commit private research, original records, backups, review packages or application source. Generate a new site manifest; do not silently expand its file allowlist.
7. The owner manually runs the release workflow and supplies the approved SHA-256. There is no private-repository/Drive ingestion, push-triggered or scheduled publishing. Manual workflow inputs must record authorization actually given; they do not invent it.
8. Verify the public HTTPS URL, project-subpath assets, metadata, PDF retrieval and a physical iPhone/Safari after launch. Keep the previous approved release and digest for a separately authorized rollback.

The owner account and release operator are trusted. Someone already authorized to rewrite the repository/workflow can change these controls; the documented approval process and repository access management remain necessary. Credentials are supplied by GitHub only at workflow runtime, never stored in the portfolio.

For W3, keep public RSS empty until an approved milestone has a verified published release receipt. Acceptance of a development checkpoint does not authorize an announcement. Email activation, controlled confirmation tests and every mailing require separate owner authorization. A later approved signup URL changes the release digest and requires a new manifest. Rollback must retain milestone identities and notification history; it cannot recall delivered email or RSS reader caches.
