A real-device checkpoint

Magic’s Decision Desk has moved from simulated passkey testing to recorded validation on real devices. The M7 project report documents successful iPhone Face ID and Windows Hello authentication in an isolated test environment. All 12 steps in the device test plan passed; 14 of 14 simulated unauthorized requests were rejected.

The plan covered more than successful sign-in. It exercised enrollment, cancellation, device removal, expired codes, emergency locking and access refusal. Trading stayed disabled. The temporary server, access route and disposable server-side store were removed after testing. Test passkeys could remain on the devices; the removed test environment no longer recognizes them.

What testing changed

The device exercise also exposed useful gaps: some refusals and cancelled prompts were not represented in the audit trail, and a recent sign-in could still count as authorization for a device change. M7f addressed those behaviors in development rather than treating a successful sign-in as the end of the work.

The hardening adds fresh, single-use authorization for device changes, strengthens server-side refusal of paper-trade requests, and improves security auditing, emergency locking and backup/recovery checks. These are implementation and test results, not an announcement of a production service.

The evidence, with its limits

The M7f development report records 448 repository tests run, with the suite finishing OK and one test skipped. Its browser rehearsal passed 31 of 31 checks using simulated passkeys and disposable data. Those browser checks are separate from the earlier M7 real-device test plan.

M7f changes to device authorization and the device-side emergency lock still need a focused real-device smoke test. Production setup and deployment remain separate, owner-approved steps. Passing these checks is not a claim that every security risk has been eliminated.

Where the project stands

M7 real-device validation is recorded as complete, and M7f hardening is complete in development. Production authentication is NOT DEPLOYED. Trading is DISABLED, and this authentication build refuses paper-trade writes. The portfolio presents the work; it does not provide access to the underlying application.

The next step is an approved deployment rehearsal and focused device acceptance before any production activation. The engineering lesson is straightforward: use real-device testing to challenge assumptions, turn the findings into specific corrections, and keep test completion separate from permission to deploy.

Evidence scope: recorded project results and source inspection. These application tests were not independently rerun for this portfolio announcement.
