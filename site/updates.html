MAGIC’S FITNESS COMPANION / PERSONAL iPHONE APP

An iPhone update, with existing data preserved

An accepted update to the app I already use—not a first installation or a public app launch.

Installation and owner acceptance recorded: 9 November 2026 · Version 1.7.1, build 33. The installed app displays the name MrMagic Fitness Companion.

What I checked on my iPhone

The MacBook development receipt records a successful in-place installation without uninstalling the existing app. I confirmed normal launch, familiar workouts, body/scale history, settings and the data library. A cold reopen retained the expected records and the Plan, Today and Ask experience.

I checked Ask MrMagic’s extra-set answer and entry points from Today, Plan, Activity, Protein, More and Progress; scrolling in lower More and Progress; keyboard clearance in Plan; and the original saying card with “Show another.” Data comparisons also supported preservation, while the Health library continued its normal background exports. This is not a claim that every file stayed byte-identical.

Useful help, with a clear boundary

The app’s Ask MrMagic answers supported how-to questions locally using deterministic content. It does not read personal records, store queries or call an external AI service. This working app-help feature is separate from this website’s six-topic Q&A and the planned private cross-workspace assistant.

What is still unverified

Full sheet-by-sheet coverage, VoiceOver and largest-text runtime checks remain outstanding. No new live scale or watch exchange was tested. An existing workout-count test defect remains unresolved; supplemental sets do not yet change the legacy two-set totals. No uninterrupted watch reporting or native Apple Watch application is claimed.

The physical-iPhone results are owner-confirmed and recorded by MacBook Fitness Codex; Portfolio Codex did not rerun the app tests or operate the phone. The Fitness page separates three owner-approved personal build 33 iPhone Mirroring views—Today, Activity and Weight—from earlier computer-test images and approved design artwork. The displayed readings are dated and energy coverage is incomplete. The application remains personal-use software; it was installed and launched on two iPhones through Apple TestFlight on November 10, 2026, and it is not released on the App Store.

MAGIC’S DECISION DESK / SIGN-IN AND SECURITY TESTS

From simulated sign-in to real-device validation

Magic’s Decision Desk completed a device sign-in test plan and a later round of security improvements in development.

Test results recorded: 3 November 2026 · Based on reviewed project reports and implementation tests.

Testing on real devices

Magic’s Decision Desk has moved from simulated passkey testing to recorded validation on real devices. The device-test report records successful iPhone Face ID and Windows Hello sign-in in a separate test environment. All 12 steps in the device test plan passed; 14 of 14 simulated unauthorized requests were rejected.

The plan covered more than successful sign-in. It exercised enrollment, cancellation, device removal, expired codes, emergency locking and access refusal. Trading stayed disabled. The temporary server, access route and disposable server-side store were removed after testing. Test passkeys could remain on the devices; the removed test environment no longer recognizes them.

What testing changed

The device exercise also exposed useful gaps: some refusals and cancelled prompts were not represented in the audit trail, and a recent sign-in could still count as authorization for a device change. The later security revision addressed those behaviors in development rather than treating a successful sign-in as the end of the work.

The hardening adds fresh, single-use authorization for device changes, strengthens server-side refusal of paper-trade requests, and improves security auditing, emergency locking and backup/recovery checks. These are implementation and test results, not an announcement of a production service.

The evidence, with its limits

The later security report records 448 repository tests run, with the suite finishing OK and one test skipped. Its browser rehearsal passed 31 of 31 checks using simulated passkeys and disposable data. Those browser checks are separate from the earlier real-device test plan.

The later changes to device permissions and emergency locking still need a short, focused test on real devices. Setup for everyday use remains a separate step requiring owner approval. Passing these checks is not a claim that every security risk has been eliminated.

Where the project stands

The initial real-device sign-in tests are complete, and the later security changes are complete in development. Production authentication is NOT DEPLOYED. Trading is DISABLED, and this authentication build refuses paper-trade writes. The portfolio presents the work; it does not provide access to the underlying application.

Next, rehearse setup and retest the changed behavior on real devices before any owner-approved activation. The engineering lesson is straightforward: use real-device testing to challenge assumptions, turn the findings into specific corrections, and keep test completion separate from permission to deploy.

These results come from recorded project tests and code review. The application tests were not rerun for this portfolio story.
